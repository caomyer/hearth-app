# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Check everything with `uv run ruff check && uv run ruff format --check && uv run mypy && uv run pytest`; CI runs the same (`.github/workflows/ci.yml`).
- Never commit real account identifiers, balances, payees or personal names, anywhere. Fixtures and the demo (`src/hearth/demo.py`, `tests/household.py`) are invented.
- The privacy boundary is the product. The rules live in `src/hearth/access.py`, are asked only through `src/hearth/disclosure/gate.py` (the one importer of `access`), and are applied only in the `hearth.disclosure` package; pages render views from `Disclosure` and nothing else. The behavioural crawl in `tests/test_privacy_boundary.py` enforces the boundary; `tests/test_architecture.py` only prevents erosion. See `docs/privacy-boundary.md`.
- Architecture fitness tests of the import graph (`tests/test_architecture.py`) are a deliberate, allowed category here: they catch a second call site the crawl might not cover before it ships. They are not proof of behaviour and cannot see aliasing, re-exports, `getattr` or dynamic imports.
- A new route must be added to `ROUTERS` in `src/hearth/web/routes/__init__.py` and taught to `tests/test_privacy_boundary.py`, which fails the build otherwise. Anything private must answer exactly like something missing: raise `Concealed`.
- Server-rendered only: never add an endpoint that returns data as JSON.
  The Mac app's stdin/stdout bridge (`hearth.native`) is the one exception and opens no port; it answers `signed_out` until a member signs in over it through `hearth.auth.sign_in`, and only `hearth.native.bridge` builds a `Doorway` (`docs/native.md`). The one place figures leave as data is the native app's doorway, `hearth.native`: standard input and output of a process the app starts, never a port, built from `Disclosure` views alone and held to every rule a page is (`docs/native.md`). A new screen goes in `doorway.SCREENS`, which `tests/native/test_doorway.py` then crawls for leaks.
- The Mac app lives in `apple/` and computes nothing: it carries hearth's Python as its engine (`apple/README.md`). Check it with `swift test --package-path apple/HearthKit`, and the bundled engine with `apple/scripts/check-engine.py`. `xcodebuild` needs `DEVELOPER_DIR` pointed at an Xcode. Beancount is GPL-2.0-only, so the app is for private use, shared with its source.
- No live Plaid call without the captain's approval for that step: the client refuses unless the run was started with `--approve-plaid OPERATION` (or `hearth plaid ... --approved`); the Mac app gives it only by starting `hearth bridge --approve-plaid` for the switches the person turned on in its Settings, never over the wire, and a bridge cannot be approved for `link` or `remove`. Reading a brokerage's holdings is its own operation, `holdings`, never a `read`: its first call adds Plaid's Investments product to the Item (`hearth.plaid.holdings`). So is reading its trades and dividends, `activity` (`/investments/transactions/get`, `hearth.plaid.activity`), whose first call adds a second subscription; they are kept in the feed for a ledger outside hearth and never booked. Build and test against `hearth.plaid.fake`, which the demo also uses. What Plaid sends lives in `feed.sqlite3`, never the app database, except a brokerage's prices, which are market facts kept with their provenance in the app database's `price` table (`docs/valuation.md`). See `docs/connections.md`.
- Plaid Link opens only on `/connect/link` and `/connect/oauth`, the two pages that set their own CSP and `Cross-Origin-Opener-Policy` (`same-origin-allow-popups`, or the bank's OAuth window is severed); tokens carry the redirect URI only when hearth serves HTTPS, which Plaid's production requires (`docs/connections.md`).
- `hearth.log` in the data dir (`hearth.runlog`) records Plaid operations, outcomes, error codes and request ids; never log a body, token, key, balance, account or payee, and pass anything from a browser through `runlog`'s shape checks first.
- An Item enters hearth only through Link (`Connector.finish_link`) or `hearth plaid adopt` (`Connector.offer`/`adopt`, for an Item made outside hearth); both seal its token with `TokenVault.put` and register it with `Registry.add`. Never add a third way in, and never take a token as a command-line argument.
- `hearth export` (`hearth.plaid.export`, schema `buzz.plaid.v4`) is the only thing a ledger kept outside hearth takes from it: reads no ledger, makes no live call, holds one member's accounts, and names a pair's other side only if that member owns it. The reader lives in beancount_self (`ledger/bank_sync`, `PlaidImporter`), so a change of shape is a change of schema.
- Figures come from `hearth.books`: one recompute, daily and on request, never on page load. Every sync, the morning's, the Mac app's sync control or `hearth plaid sync` by hand, goes through `hearth.refresh.sync_then_recompute` (a long-running process through one `hearth.refresh.Refresher`) and says whether the books now hold it; never add a fetch that ends without a recompute. A `hearth plaid` command runs in its own process, so a serving hearth sees its changes only through `books.standing` (`Bookkeeper.recompute_on_change`): anything new a recompute reads must be part of it. No ledger is the default: hearth derives its own entries in memory from mappings and the feed (`hearth.ownbooks`), over the household's own ledger only when it has one: the base it imported and froze (`hearth import-ledger`, or the Mac app once, both through `ledger_import.import_ledger`; `hearth.base`), or, for now, one inherited at `HEARTH_LEDGER`, never both. Each recompute also notes every connection's last successful sync, which decides coverage of an account once the books hold entries booked from that connection (`books.vouched`, `figures.covers`); an account carried on from the base is vouched for like hearth's own, the base's entries holding the bank's rows counting as that connection's, and any other account a frozen base opens only through the base's own last day on it (`books.vouched_over_base`), never a later sync; so a sync recomputes when it finishes. `uv run hearth demo` (or `--from-zero`) serves an invented household through the same path.
- "Today" is always the local calendar day of the injected clock, `clock().astimezone().date()`, never `.date()` of its UTC moment. Tests say "the clock reads day D" with `tests.household.noon(D)`; CI runs the suite again at UTC+14 and UTC-11, where a day taken in UTC is a day off.
- Each recompute writes `books.beancount` to the data dir: an output, never an input. Never read it back or parse it for figures; derive from the feed and app db instead (`docs/books.md`). It holds every entry of the books as laid over, the base's included, never an include of a ledger, and runs no plugin again (`ownbooks.render`), so it is exactly the books computed. The base in `ledger-base/` beside it is the opposite: an input, written once at its import and never again.
- Every ledger hearth reads, the base, one at `HEARTH_LEDGER` or one `hearth compare` is given, is loaded only through `books.load_ledger` (or `load_entries`), never `loader.load_file`, whose pickle cache writes beside the ledger; it runs beancount's own plugins and no other (`books.runs`). Never write at or beside a ledger outside the data dir. The base is refused unless its files match its digest and it reads nothing outside itself (`tests/test_ledger_import.py`). See `docs/real-ledger.md`.
- Which of the base's accounts each connected account is comes from `hearth.matching` (`hearth match-accounts`): proposed from the Plaid ids base entries carry, hearth's `source` and a bare `plaid-id` alike, else by content, and confirmed as the ordinary mapping (`Registry.confirm`) onto an account already claimed by the connection's holder; a match never changes ownership, and an account comes to be owned only through `accounts.claim_all` (`hearth add-account`, or an admin's `assign_owners` in the app), never reassigned. A matched account is carried on (`hearth.carrying`): the base holds its history before its cut-over, derived each recompute from the base alone (`carrying.cut_over`), and hearth books the bank's rows from then on that the base does not hold by either id or by content; a row before it the base lacks is counted, never booked. Only depository, credit and loan accounts the base does not close, whose cut-over has come by the household's own day, are carried (`carrying.carries`, `carrying.postponed`); a brokerage is not yet. Days between the cut-over and the bank's first row are known by neither and never read as complete (`books.unseen_between`). No sequence of actions hearth allows may make a recompute fail because of carrying: nothing may post onto a carried account that its difference does not see, so no row is moved onto one, no account a ruling now moves a row into is matched, and any ruling that would still land one there leaves its row unreviewed (`review.decision.guarded`). A match may be corrected, its rows moving with it, until a member rules on a row carried on the account or its reconciling entry (`books.begun`); from then its match and the base are fixed. An account hearth kept itself moves onto the base's only through `hearth match-accounts` and only when carrying holds every row it booked; rulings follow it through `carried_over` (`docs/real-ledger.md`).
- Feed rows reach the books only through the import, `hearth.plaid.booking`, derived afresh on every recompute: it takes each transaction once by `Registry.connected_twice()` (a removed connection gives way to the working one; two working ones are refused until one is removed), books no pending row, pairs first (`hearth.plaid.pairing`: a bank's payment to a connected card is one transfer; a leg nothing pairs with is flagged against `Equity:Review:TransferPending`), writes every `source` with `connections.plaid_source`, and leaves an inherited ledger's accounts to it, except an imported base's carried accounts, whose pairs are booked by what the base holds of each leg (`booking._legs`, `docs/books.md`, `docs/pairing.md`).
- A connected account's balance is its opening balance, derived each recompute from the bank's current balance less the posted rows and asserted back against it (`hearth.plaid.opening`); a disagreement fails the recompute, and one that cannot be derived stays not known (`books.unanchored`), never a sum of rows or a guess. A carried account has no opening: its bank's balance is asserted against the base at its cut-over plus the rows since, and a disagreement is one reconciling entry dated the cut-over against `Equity:Ledger-Bank-Difference`, flagged and in Review, derived from those three alone so it never recurs, never failing the recompute; while unconfirmed the account is never shown as matching its bank (`opening.Carrying`, `books.reconciling`). Openings and assertions are balances, not history: keep them out of coverage and transaction lists (`docs/books.md`). A brokerage account is anchored the same way at what its brokerage last reported it holds (`Feed.holdings`, `balance: "holdings"`), dated that day and claiming nothing before it (`books.positioned`); never derive positions from activity, even where activity is fetched.
- An account a member names (`accounts.name_account`) is one hearth does not see: opened with `seen: "moves-only"`, in `books.unseen`, never valued and never `awaiting`, so totals say "without" it rather than "not known yet". So is a claimed account nothing opens (no ledger, no connection: `ownbooks.Derived.unfed`), which takes no moves. "Not known yet" is only for a balance about to arrive (`Household.arriving`, `books.unanchored`). Never read its balance from its rows; that is the rejected bucket design (`docs/books.md`, "Accounts hearth does not see").
- A row's suggested category comes only from `hearth.proposals`, derived afresh each recompute in the order and thresholds `docs/review.md` states ("Suggestions, and why"), merchants matched by `hearth.merchants` alone. It learns only what `access.may_learn` allows (accounts with exactly the row's owners, rulings by one of them). A ruling makes its row immune to what is learned: an accept holds while the bank's own inputs (`ids.says` and the bank's category, `review-bank`) are unchanged, a pre-learning accept while `booking.proposal` still names its account (`review.decision`); never make an accepted row depend on anything learned. A suggestion never accepts anything, and its reason is told only to the row's reviewers.
- Every income and expense account has a kind (`hearth.categories`), guessed from generic words in its name and stored only when a person sets it (`hearth categories`); every spending figure counts only `Books.spends`, never "not spending", whose amount is in what was left over.
- Statements (`hearth.disclosure.statements` over `hearth.reports.statements`) read only the parts a viewer may see in full (`access.may_read_statements`), decided once before any figure, never a part at a coarser grain; they read `Books.ledger`, which each recompute builds once, never the history or the price table on an ask, and their change in net worth adds up to the balance sheet with any difference shown as its own line (`docs/reports.md`, "Statements").
- Every imported row is in the books; review rulings live in the app database and each recompute lays them over the ledger, which hearth never writes. Unreviewed rows stay `!`, and any new total must say how much rests on them without revealing another member's queue (`docs/review.md`).
- Pages follow `design/` exactly: the app serves `design/hearth.css` and `design.js` byte for byte (a test checks); additions go in `src/hearth/static/app.css`; templates link every static file through `asset()` (`hearth.web.templating`), whose content digest stops a browser drawing new markup with a cached old stylesheet.
- `design/` belongs to the design crew; do not edit it from app work.
