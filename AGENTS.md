# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Check everything with `uv run ruff check && uv run ruff format --check && uv run mypy && uv run pytest`; CI runs the same (`.github/workflows/ci.yml`).
- Never commit real account identifiers, balances, payees or personal names, anywhere. Fixtures and the demo (`src/hearth/demo.py`, `tests/household.py`) are invented.
- The privacy boundary is the product. The rules live in `src/hearth/access.py`, are asked only through `src/hearth/disclosure/gate.py` (the one importer of `access`), and are applied only in the `hearth.disclosure` package; pages render views from `Disclosure` and nothing else. The behavioural crawl in `tests/test_privacy_boundary.py` enforces the boundary; `tests/test_architecture.py` only prevents erosion. See `docs/privacy-boundary.md`.
- Architecture fitness tests of the import graph (`tests/test_architecture.py`) are a deliberate, allowed category here: they catch a second call site the crawl might not cover before it ships. They are not proof of behaviour and cannot see aliasing, re-exports, `getattr` or dynamic imports.
- A new route must be added to `ROUTERS` in `src/hearth/web/routes/__init__.py` and taught to `tests/test_privacy_boundary.py`, which fails the build otherwise. Anything private must answer exactly like something missing: raise `Concealed`.
- Server-rendered only: never add an endpoint that returns data as JSON.
- No live Plaid call without the captain's approval for that step: the client refuses unless the run was started with `--approve-plaid OPERATION` (or `hearth plaid ... --approved`). Reading a brokerage's holdings is its own operation, `holdings`, never a `read`: its first call adds Plaid's Investments product to the Item (`hearth.plaid.holdings`); trades (`/investments/transactions/get`) are not fetched. Build and test against `hearth.plaid.fake`, which the demo also uses. What Plaid sends lives in `feed.sqlite3`, never the app database, except a brokerage's prices, which are market facts kept with their provenance in the app database's `price` table (`docs/valuation.md`). See `docs/connections.md`.
- Plaid Link opens only on `/connect/link` and `/connect/oauth`, the two pages that set their own CSP and `Cross-Origin-Opener-Policy` (`same-origin-allow-popups`, or the bank's OAuth window is severed); tokens carry the redirect URI only when hearth serves HTTPS, which Plaid's production requires (`docs/connections.md`).
- `hearth.log` in the data dir (`hearth.runlog`) records Plaid operations, outcomes, error codes and request ids; never log a body, token, key, balance, account or payee, and pass anything from a browser through `runlog`'s shape checks first.
- An Item enters hearth only through Link (`Connector.finish_link`) or `hearth plaid adopt` (`Connector.offer`/`adopt`, for an Item made outside hearth); both seal its token with `TokenVault.put` and register it with `Registry.add`. Never add a third way in, and never take a token as a command-line argument.
- Figures come from `hearth.books`: one recompute, daily and on request, never on page load. Every sync, the morning's or `hearth plaid sync` by hand, goes through `hearth.refresh.sync_then_recompute` and says whether the books now hold it; never add a fetch that ends without a recompute. A `hearth plaid` command runs in its own process, so a serving hearth sees its changes only through `books.standing` (`Bookkeeper.recompute_on_change`): anything new a recompute reads must be part of it. No ledger is the default: hearth derives its own entries in memory from mappings and the feed (`hearth.ownbooks`), over a ledger at `HEARTH_LEDGER` only when a household inherits one. Each recompute also notes every connection's last successful sync, which decides coverage of an account once the books hold entries booked from that connection (`books.vouched`, `figures.covers`), so a sync recomputes when it finishes. `uv run hearth demo` (or `--from-zero`) serves an invented household through the same path.
- Each recompute writes `books.beancount` to the data dir: an output, never an input. Never read it back or parse it for figures; derive from the feed and app db instead (`docs/books.md`).
- An inherited ledger is the household's and read-only: load it only through `books.load_entries`, never `loader.load_file`, whose pickle cache writes beside the ledger (`tests/test_books.py`). See `docs/real-ledger.md`.
- Feed rows reach the books only through the import, `hearth.plaid.booking`, derived afresh on every recompute: it takes each transaction once by `Registry.connected_twice()` (a removed connection gives way to the working one; two working ones are refused until one is removed), books no pending row, pairs first (`hearth.plaid.pairing`: a bank's payment to a connected card is one transfer; a leg nothing pairs with is flagged against `Equity:Review:TransferPending`), writes every `source` with `connections.plaid_source`, and leaves an inherited ledger's accounts to it (`docs/books.md`, `docs/pairing.md`).
- A connected account's balance is its opening balance, derived each recompute from the bank's current balance less the posted rows and asserted back against it (`hearth.plaid.opening`); a disagreement fails the recompute, and one that cannot be derived stays not known (`books.unanchored`), never a sum of rows or a guess. Openings and assertions are balances, not history: keep them out of coverage and transaction lists (`docs/books.md`). A brokerage account is anchored the same way at what its brokerage last reported it holds (`Feed.holdings`, `balance: "holdings"`), dated that day and claiming nothing before it (`books.positioned`); never derive positions from activity, as no trades are fetched.
- An account a member names (`accounts.name_account`) is one hearth does not see: opened with `seen: "moves-only"`, in `books.unseen`, never valued and never `awaiting`, so totals say "without" it rather than "not known yet". So is a claimed account nothing opens (no ledger, no connection: `ownbooks.Derived.unfed`), which takes no moves. "Not known yet" is only for a balance about to arrive (`Household.arriving`, `books.unanchored`). Never read its balance from its rows; that is the rejected bucket design (`docs/books.md`, "Accounts hearth does not see").
- Every imported row is in the books; review rulings live in the app database and each recompute lays them over the ledger, which hearth never writes. Unreviewed rows stay `!`, and any new total must say how much rests on them without revealing another member's queue (`docs/review.md`).
- Pages follow `design/` exactly: the app serves `design/hearth.css` and `design.js` byte for byte (a test checks); additions go in `src/hearth/static/app.css`.
- `design/` belongs to the design crew; do not edit it from app work.
